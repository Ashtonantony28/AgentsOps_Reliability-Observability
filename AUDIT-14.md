# AUDIT-14: API, SDK and tests (round 6)

Audited at `86315ff` (everything through PR #55 merged) by a session that wrote none of the code. Scope: the round-5 changes as API and SDK contracts (SG-A11.1 per-org pool slots, rebuild slots and batch lists, #53; SG-A11.2 the compile cache off the event loop, #52; SG-A12.2 per-loop guard and push locks, #54; SG-A12.1 per-slice prefix checkpoints, waiting and takeover, `CHECK_DEADLINE_S`, the request-disconnect stop and the new `503 check_timeout` from `/api/trace-policies/check`, #55), how both SDK clients and `@guard` handle that 503, overlapping and abandoned checks through the real app and a real server, and test quality, including a mutation probe of the round-5 fixes. Checker correctness and security are AUDIT-13's, which ran in parallel. Since then the default branch gained SG-A13.1 (#57), SG-A13.2 (#58) and SG-A13.3 (#59); each finding below says whether it still holds at `632b62b`, and A14-2 is in code #58 added. Known and accepted gaps from AUDIT-1 to AUDIT-12 and the PLAN.md results are not re-reported.

**Result: 0 critical, 0 high, 2 medium, 3 low.** A14-1 is the stored-trace half of `/check`: SG-A12.1 made a long prefix resume from, wait for and stop with other checks, but a check of a streamed trace whose monitor state no longer fits (any policy edit for the agent, or a Redis loss) rebuilds it from spans outside all of that. AUDIT-13 found the same in parallel (A13-5) and SG-A13.1 (#57) fixed it on the default branch: this audit's tests for it fail at `86315ff` and pass at `632b62b`, so no sub-goal is proposed. A14-2 is new with SG-A13.2 (#58): a streamed trace whose backlog passes the new 16 MiB body limit loses the rest of its events, because the SDK ends the stream on that 413 instead of splitting the append. It is PLAN.md sub-goal `SG-A14.1`.

Failing tests, each `xfail(strict=True)` and failing at `86315ff` at its final assertion after its control assertions pass: `backend/tests/audit/test_audit_14.py` (A14-1, real app, on SQLite and Postgres 16) and `sdk/tests/test_audit_14.py` (A14-2, the SDK's `FakeServer`). The A14-1 pair XPASSes on the default branch (SG-A13.1), so whoever merges this branch there removes those two markers; the A14-2 test fails on both, since #58 changed no SDK code. Run them with `cd backend && pytest tests/audit/test_audit_14.py -q --runxfail` (add `TEST_DB=postgres` for Postgres) and `cd sdk && pytest tests/test_audit_14.py -q --runxfail`. ## Medium

### A14-1 A check's span rebuild neither resumes nor stops (API, availability)

A `/check` with a `trace_uid` first positions a monitor after the trace's stored events (`precheck_monitor`): it restores the append path's Redis state or its own cached rebuild, and if neither fits rebuilds from spans under the Redis lock `lock:monitor-rebuild:<trace>` (`timeout=30, blocking_timeout=5`), then caches the result. The state no longer fits after any policy create, update, enable or disable that changes the agent's policy set (the restore checks policy ids and plan digests), after a Redis loss, or when the stored trace moved on since. SG-A12.1 (#55) gave the prefix half of a check its overlap and stop contract: a check resumes from what any other check of the same history stepped, waits for a slice another is stepping, and stops between slices once its request is gone or past `CHECK_DEADLINE_S`, answered `503 check_timeout`. The rebuild half has none of it:

- **A later check starts over.** A check that arrives while another is rebuilding the same trace waits 5 s for the lock, gets `False`, and rebuilds the whole trace itself, unlocked; one queued for a rebuild slot (`FairSlots(MAX_CONCURRENT_REBUILDS)`) does not look at the cache again once it gets the slot.
- **A rebuild never stops.** `_replay` runs to the end whatever `gone()` says, and the deadline is only checked between prefix slices, so a check that needs a rebuild is answered 200 at 60 s and more, against SG-A12.1's "past `CHECK_DEADLINE_S` (30 s), answered 503".

Measured (test app, SQLite): one check of a 4 000-event streamed trace at 3 996 units with its state stale took 8.6 s; 8 checks of it started a second apart took 13.0, 37.2, 53.3, 50.5, 52.1, 62.7, 65.4 and 6.1 s, all 200, rebuilding 28 000 events in all (7 full rebuilds; the last arrived late enough to restore). The work is the org's own pool share, so SG-A11.1 keeps other orgs' turns, but for the agent every check in that window fails open (or blocks, with `fail_closed`), and the trace's own appends rebuild on the same slots. Through uvicorn with the sync client's `@guard` on a streamed trace of 4 000 events after a small policy was added, the SDK's serial flow limits the pile-up: the first guarded call's check timed out at 2 s and failed open, its rebuild ran on, and the push of that call's event rebuilt the trace again on the append path (which supersedes the check's cached rebuild) and passed the SDK's 10 s append timeout: two full rebuilds, calls stalled 12.2 s and 8.5 s, then 0.1 to 0.2 s. Concurrent `t.check`/`acheck` calls, several processes checking one trace, or any client re-sending a check it gave up on get the full pile-up.

Fix direction: give the rebuild SG-A12.1's slice contract: checkpoint it per slice under a key of the trace, its next seq and the plan digests (the prefix checkpoints' seed already is), so a later check resumes from it or waits for its slice, look at the cache again after a rebuild slot is granted, and check `gone()` and the deadline between rebuild slices (503 `check_timeout`, what it built kept).

Fixed on the default branch: SG-A13.1 (#57) rebuilds under the lock in turns of `SLICE_WAIT_S` with the deadline and request looked at between them, renews the lock between slices, and saves a stopped rebuild for the next check to resume. Both tests below fail at `86315ff` and pass at `632b62b`.

Tests: `test_check_of_a_stored_trace_resumes_from_a_rebuild_still_running` (one 1 001-unit `block` policy, 2 000 stored events, a policy added; the first check's rebuild is paused 7 s half done, and a second identical check rebuilds all 2 000 events again after its 5 s lock wait) and `test_a_checks_rebuild_stops_once_its_request_is_gone` (control: a long prefix check stops after 3 slices with 503; the stored trace's check rebuilds all 2 000 events and answers 200).

### A14-2 A streamed backlog over the body limit ends the stream (SDK + API, since #58)

SG-A13.2 (#58) answers a request body over 16 MiB with 413 `request_too_large` (`max_bytes`) before reading it, on every route, and records that the SDK "stops the stream on it from an append". A streamed trace sends all its pending events in one append (`Trace._batch`: everything from `_sent`, capped only by a `max_events` the server gave earlier), and events carry their `input` and `output`; while the server is unreachable or answering 5xx, the backlog grows with every event. Once it passes 16 MiB, `push_outcome` reads the 413 as `fatal` (only `policy_work_too_large` with `max_events` is split): the SDK sets `_dead`, drops the batch and sends nothing more for the trace, `final` included. The server keeps what it had, and the idle sweep closes it an hour later and batch-checks it without the dropped events, so a violation in them is never recorded, and nothing falls back to the whole-trace upload (`__exit__` uploads only unstreamed traces). Checks of the trace still go to the server with the undelivered events as their prefix (kind, name, status and attrs, which stay small), so enforcement holds; the record does not. An LLM agent's events with a few hundred KB of prompt and completion each pass the limit after a few dozen events of outage. Before #58 the app took any size (a proxy's limit gave the same outcome, which PLAN reads as an outage only for `/check`). SG-A13.2 lists the bulk path's version as a known gap (a bulk batch over the limit is re-buffered and never drains); the append path's loss is not listed.

Fix direction: on 413 `request_too_large` send the append again in smaller pieces (halving, or sized from `max_bytes` and the batch's bytes), as `max_events` does for policy work, and drop only a single event over the limit (as a refused one, the stream going on).

Test: `sdk/tests/test_audit_14.py::test_backlog_over_the_body_limit_is_split_not_dropped` (three 5xx replies grow the backlog to 4 events, the fourth push gets the 413; the stream ends with none of the 5 events delivered).

## Low

- **A14-3** `docs/policy-dsl.md` (Limits) still says "A `/check` is always answered", and `trace_service.precheck`'s docstring opens the same way; since #55 a check is `503 check_timeout` once its request is gone or past `CHECK_DEADLINE_S` (30 s). Neither the docs, `sdk/README.md` nor PLAN.md's HTTP contract row for `/check` lists the 503 or the deadline. For SDK users two consequences are undocumented: a `check_timeout_s` over 30 s is capped by the server (the check fails at 30 s, following `fail_closed`, though the reply says "resend it to resume"), and a check that timed out is not wasted (the next check resumes from what it stepped), which is what makes the default 2 s timeout workable on long unstreamed traces. The SDK's handling itself matches the contract (follows `fail_closed`, `error="http 503"`, both clients and `@guard`; `sdk/tests/test_audit_14.py`). Unchanged at `632b62b`, whose docs still say "always answered".
- **A14-4** `compile_all` takes the fast path when `all(k in _compiled for k in keys)` and then calls `_compile` for each key on the event loop. `_compile` re-reads under the lock, but between the check and the read a default-executor thread compiling another request's misses can insert past `COMPILE_CACHE_SIZE` and evict one of these keys, which is then parsed and planned on the loop (up to tens of ms per tag-heavy policy). It needs a cache already thrashed past 2 048 entries, which PLAN's SG-A11.2 low accepts as costing a thread's time, not the loop's. Fix: the fast path reads without compiling and falls back to the thread on any miss. Unchanged at `632b62b`.
- **A14-5** Mutants of the round-5 fixes the suite does not kill: see **Mutation probe**.

## Mutation probe

29 one-line mutants of the round-5 API and SDK fixes (PRs #52 to #55), each applied to a temporary copy of the repo and run against the tests of the code it changes (`python backend/scripts/mutants_audit14.py`; backend rows against `test_policy_work.py`, `test_audit_11/12/14.py`, or the batch-queue or compile test files, SDK rows against the whole SDK suite). AUDIT-14's own xfail tests are left out. The harness now gives a mutant 900 s: two mutants hung their tests, which counts as a kill.

- **Killed (20)**: SG-A11.1: turn order within and across orgs (`_release` putting an org back at the front, `_free` never charged), cancelled waiters' slots, check slices keyed by org (`test_one_orgs_policy_work_does_not_queue_another_orgs`), rebuild slots keyed by org (hung), the batch lists' push and pop scripts, the `TraceBusy` retry's trace, the Redis-down fallback, an upload's batch check queued for the wrong org. SG-A11.2: the fast path always taken (compile on the loop), unparsable sources not cached, `org_cost` without unused tags. SG-A12.1: stall takeover on any moving slice, a waiter waiting without `SLICE_WAIT_S` (hung), the 503 code, `is_disconnected` not passed. SG-A12.2: one asyncio lock for every loop, the push lock dropped. SDK: a 503 `check_timeout` read as a configuration error (blocks whatever `fail_closed`) is killed only by `sdk/tests/test_audit_14.py`; it survives the suite as it was.
- **Survived (9)**, `python backend/scripts/mutants_audit14.py A14-5`; the 8 backend ones were replayed against the whole backend suite (SQLite) and survive it too (4 of them first "failed" `tests/audit/test_audit_9.py`'s two wall-clock tests, known flaky, or a Postgres test whose connection another session's run closed, none reachable from those mutants; replayed without the two timing tests they survive):
  - SG-A11.1 on the API: `run_sliced` never handing its slot on between slices (`if self._waiting:` → `if False:`), and `run_sliced` taking every org's slots under one key. Both undo A11-1's fix for appends, upload `block` checks and rebuilds: one org's long appends would again hold the two pool threads while another's wait. A11-1's test measures only checks, which since SG-A12.1 take a slot per slice, so nothing tests the sliced jobs' turns. Also `_in_pieces` not offering the GIL between pieces (`time.sleep(0)` removed; a timing property no test pins).
  - SG-A11.1 in the batch: the idle sweep queueing its closed traces under the wrong org; the `enqueued` fixture drops the org, so no test sees which org's list a trace goes on except through `test_audit_11`'s upload path.
  - SG-A11.2: the cache's LRU order (`move_to_end` dropped, or `popitem()` evicting the newest entry): no test fills the cache past `COMPILE_CACHE_SIZE`; create and update parsing on the event loop again (`_parse_or_422` without `to_thread`): the stall test covers `active_policies` only.
  - SG-A12.1: a finished slice's entry never removed from `_stepping` (a per-process map that then grows by one entry per slice ever stepped, holding its snapshot); no test looks at the map after a check.
  - SG-A12.2: the async guard queueing on a fresh `asyncio.Lock` per call instead of the loop's (the threading lock still excludes, so only the FIFO order of a loop's guarded calls is lost); no test checks that order.

## Round-5 fixes re-checked

- **SG-A12.1 (#55)**: a long prefix saves each checkpoint as its slice is stepped and resumes from the newest before every slice; a slice another check is stepping is waited for while its pieces move and taken over once stalled; checkpoint keys cover org, stored trace and next seq, plan digests and each event's kind, name, status and attrs. Through uvicorn the disconnect stop works for both SDK clients: the server stepped at most one slice after the client's timeout, and repeated checks of a 3 000-event history at 1 001 units resumed until one answered `allowed: false`. The 503 envelope is the app's usual `{"error": {"code", "message", "details"}}`. Holds, except A14-1 (the rebuild half) and A14-2 (docs).
- **SG-A11.1 (#53)**: `FairSlots` hands slots round robin by org, cancelled waiters return a handed slot, and a job between slices yields only to a waiter; the batch lists keep the invariant "an org is on the turn list iff its list is non-empty" in one Lua script each way, a `TraceBusy` retry keeps its trace, and without Redis the trace is queued by id. Holds; test gaps in A14-4.
- **SG-A11.2 (#52)**: create, update and validate parse in a thread; `active_policies` and `_check_org_limits` compile misses in one thread call, unparsable sources cached as `None`; `org_cost` charges unused tags; a huge integer is a `PolicyParseError`. Holds, except A14-3.
- **SG-A12.2 (#54)**: guard and push asyncio locks per running loop, the shared threading lock across loops; `asyncio.run` per step works. Holds (the open low on two loops' concurrent pushes is PLAN's).

## Not findings

- The SDK never resends on `503 check_timeout` within one check; it can't usefully, since the server answers it only when the SDK has already gone (its own timeout) or after 30 s, past any default budget. The next guarded call's check resumes instead.
- Abandoned checks behind a proxy that keeps the upstream connection open run to the deadline, but each slice they step is saved and waited for by later checks, so they do useful work, not duplicate work.
- `request.is_disconnected` under the app's only middleware (`CORSMiddleware`, pure ASGI) sees the disconnect; there is no `BaseHTTPMiddleware` to hide it.
- An append waiting for its org's pool turn holds the trace's append lock; with many orgs active its wait could approach the lock's 60 s timeout. That is AUDIT-11's lock-expiry note and AUDIT-13's (performance) to measure, not re-reported here.
- SG-A13.2 (#58) answers a bad API key before parsing the body (401 where a bad body with a bad key was 422) and a `/check` over 16 MiB with 413 `request_too_large`: the SDK reads 401 and 422 alike as configuration errors, and a 413 without `policy_work_too_large` follows `fail_closed`, as PLAN records. SG-A13.3's (#59) 429 is on registration, which the SDK never calls.
