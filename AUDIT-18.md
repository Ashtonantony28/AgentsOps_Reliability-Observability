# AUDIT-18: platform after SG-AP3 (Audit P4)

Audited at `0006c5d` (the default branch with SG-AP3.1 #75 and SG-AP3.2 #76 merged) by a session that wrote none of the code. Scope: everything merged since AUDIT-17 (`git log 9e93f64..0006c5d`): the alert tick checked in turns by org, resuming from `_resume_at`, with the rule set loaded before the deadline, a 200-rule cap per org (409 `rule_limit` under an org-row lock), and a per-rule lock + `FOR UPDATE` + dedup re-check when a rule fires (SG-AP3.1); outbound lookups with one resolver thread per queue place (`RESOLVE_THREADS = RESOLVE_QUEUE = 64`), `ORG_LOOKUPS` = 2 and `ORG_CALLS` = 10 enforced by waiting through `_Places`, `POST /api/integrations/{id}/test` limited per org, and `outbound.org` set in each dispatch task (SG-AP3.2); and regression checks of org scoping, the policy check path, ingest and the auth limits. The SG-AP3 open lows and A16-4, A16-6 are known and are not re-reported, except where a finding here is a new consequence of one (each says so).

**Result: 0 critical, 0 high, 0 medium, 2 low.** The SG-AP3 fixes hold. The two AUDIT-17 highs are closed from fresh angles: one org's many rules no longer keep a small org's rule from being checked (turns + `_resume_at`), and a handful of orgs' slow lookups no longer fail another org's outbound call (one thread per queue place, `ORG_LOOKUPS` = 2, so filling the 64 queue places now takes 32 orgs). A17-3 is closed (a rule at the channel bound is paged while another call of its org runs) and A17-4 is closed (overlapping ticks fire a rule once). No new cross-org availability, security or data-loss path reachable by a self-registered user was found, and no mutant of the SG-AP3 fixes survived. The two lows are new consequences of SG-AP3.2 (the tick's sends are now bounded per org, so an org's own slow DNS can drop its own later pages at the dispatch deadline; and `/test`'s new per-org limit is spendable by any member). Because nothing is above low, there are no `xfail(strict=True)` findings tests; `backend/tests/audit/test_audit_18.py` holds regression guards that each fail if their SG-AP3 fix is reverted.

## Summary

| ID | Severity | Finding |
|---|---|---|
| L18-1 | low | SG-AP3.2 sets `outbound.org` in each `_dispatch_all` task, so a tick's sends are now bounded per org (`ORG_LOOKUPS` = 2 lookups, `ORG_CALLS` = 10 calls); before SG-AP3.2 the tick's sends were unscoped and unbounded. An org whose own webhook/Slack hosts resolve slowly can have its own later pages in one tick wait past `DISPATCH_DEADLINE_S` (45 s) and be cancelled (logged, then dedup suppresses the rule for its window). Only that org's own pages, from that org's own slow targets. Sharpens SG-AP3.2's "an org's own slow names keep its own places busy" low onto the tick path |
| L18-2 | low | `POST /api/integrations/{id}/test` is now limited to `INTEGRATION_TEST_LIMIT_PER_MIN` (10) per org, but it depends on `get_current_user`, not a role, so any member (a viewer included) can spend the whole org's test budget, and an admin's own `/test` is then 429 for the rest of the minute. Intra-org only, and the limit is an org-shared budget by design; new surface from SG-AP3.2's contract addition |

## Method

- Read the SG-AP3 diff (`git diff 9e93f64..0006c5d -- backend/app backend/scripts backend/tests/conftest.py`) line by line against each sub-goal's Problem, Acceptance, Result and open lows: `services/alert_service.py` (the turn ordering `_in_turns`/`_rules_in_turns`, `_resume_at`, the per-rule `_rule_locks` + `FOR UPDATE` + dedup re-check, `_dispatch_all`'s `outbound.org.set`), `services/outbound.py` (`_Places`, `ORG_LOOKUPS`/`ORG_CALLS`, `RESOLVE_THREADS = RESOLVE_QUEUE`, `_Call.start`/`release`, `_resolve`'s take/give on every path, `post`'s `finally`), `routers/alerts.py` (the org-row lock + count), `routers/integrations.py` (the `/test` limit), `schemas/alert.py` and `config.py`. Also read the code the changes reach: `notification_service.py`, `violation_service.py`, `evaluation_service.py`, `tasks/alert_tasks.py`, `main.py`'s exception handler, `middleware/rate_limit.py`.
- Traced every `_Places` path for a leaked or double-counted place: take then queue-full give; the resolver done-callback give (from a resolver thread, under `_lock`); the cancelled-waiter handoff (`turn.cancel()` racing `set_running_or_notify_cancel`); `post`'s `finally` guarded by `call.refs`; the `_org_lookups` place taken before the queue check and given back on queue-full. Confirmed take/give balance on the blocked, invalid-URL, too-large, timeout, transport-error and cancelled-before-run paths, and that an org holds at most `ORG_LOOKUPS` of the `RESOLVE_QUEUE`, so 32 orgs are needed to fill it.
- Ran the SG-AP3.2 cross-org dispatch path in process (real `_dispatch_all`, stubbed `getaddrinfo`, mock transport): with 20 attacker orgs each holding a dispatch-gate permit through a slow lookup, the victim org's page is still sent — `asyncio.Semaphore`'s FIFO waiter queue plus the per-org turn order put the victim's page at the head of the wait queue, so it gets the next freed permit (one `RESOLVE_TIMEOUT_S` cycle later), within `DISPATCH_DEADLINE_S`. So the gate is not a cross-org loss path.
- Checked the turn/resume logic for a permanently-skipped or double-checked rule: `_in_turns` returns every rule each tick (`keyed[i:] + keyed[:i]`), so no rule is excluded; `summary["checked"]` is incremented before the per-rule `await`, so a rule mid-check at the deadline advances `_resume_at` past itself (no stall), and the start point rotates forward each tick, so every rule is reached within a bounded number of ticks.
- Turned the SG-AP3 fixes into regression guards (`backend/tests/audit/test_audit_18.py`), each failing if its fix is reverted, and ran them on SQLite and on Postgres 16 (`TEST_DB=postgres`).
- Mutation probe: 11 one-line mutants of the SG-AP3 fixes, replayed with `python backend/scripts/mutants_audit18.py` (see **Mutation probe**).
- Ran the full backend suite on SQLite (`--ignore=tests/api/test_postgres.py`): 1648 passed, 9 xfailed (A16-4 and the earlier audits' open xfails). `tests/audit/test_audit_18.py` on Postgres 16 (`TEST_DB=postgres`): 5 passed.

## Low

- **L18-1** The alert tick now runs each page's sends under the rule's org (`outbound.org.set(org_id)` in `_dispatch_all`, SG-AP3.2's fix for A17-2's unscoped tick calls). A side effect is that one org's tick sends are now bounded to `ORG_LOOKUPS` = 2 concurrent lookups and `ORG_CALLS` = 10 concurrent calls; before SG-AP3.2 the tick's sends were unscoped (`outbound.org` unset → no `_Call`) and ran unbounded. Under normal DNS this only serialises an org's sends slightly. But if the org's own webhook or Slack hosts resolve slowly (the org's own misconfiguration or a slow upstream), its later pages in one tick wait for a lookup place and are cancelled when `_dispatch_all` hits `DISPATCH_DEADLINE_S` (45 s); the cancelled sends are logged, and `fire_alert` has already committed, so dedup suppresses the rule until its window passes. Only that org's own pages, from that org's own slow targets; no other org is affected (the dispatch gate is FIFO + per-org turn order, so a slow org cannot cancel another org's page — verified). This extends SG-AP3.2's acknowledged "an org's own slow names can keep its own 2 lookup places busy, so that org's pages wait and fail" low onto the tick, where before SG-AP3.2 the tick alone was exempt. Repro: an org with, say, 40 enabled metric rules all crossing threshold in one tick, each with a webhook channel to a host that takes `RESOLVE_TIMEOUT_S` (5 s) to fail DNS; at 2 lookups at a time that is 20 rounds × 5 s = 100 s, past the 45 s dispatch deadline, so the later pages are cancelled and never sent. Fix direction: give the tick a larger `ORG_LOOKUPS`/`ORG_CALLS` than the API process, or count only the lookup against a wider per-org bound for tick sends.

- **L18-2** SG-AP3.2 added `POST /api/integrations/{id}/test` → `enforce_rate_limit("integration-test:{org_id}", 10)` before the integration is looked up, and `/test` depends on `get_current_user` (any role), not `require_role`. So any member of an org — a viewer, who cannot create or edit integrations — can call `/test` (for an integration an admin configured) 10 times a minute and spend the org's whole test budget, after which an admin's own `/test` is 429 `rate_limited` for the rest of the window. The limit is a per-org shared budget by design, and `/test` is a read-only connectivity check, so this is a minor intra-org nuisance, not a cross-org or privilege issue. Repro: a viewer token posts `/api/integrations/{id}/test` 11 times (the 11th is 429); an admin's `/test` in the same minute is then 429 too. Fix direction (if wanted): key the limit per user as well as per org, or gate `/test` behind `require_role("developer")` as the other integration writes are.

## Fixes re-checked

- **SG-AP3.1 (A17-1, A17-4):** rules are loaded once (`order_by(created_at, id)`), detached (`expunge_all`), and ordered into turns by org — each org's oldest rule first, orgs by their oldest rule — starting from `_resume_at` (a `(turn, org's-oldest-created_at, org_id)` key), so a tick that stops at `CHECK_DEADLINE_S` is carried on by the next; `_in_turns` always returns all rules rotated, so no rule is excluded; `summary["checked"]` is incremented before the per-rule `await`, so a rule cancelled mid-check advances the resume point past itself and the tick never stalls. A17-1 is closed: a small org's newest rule is reached within a couple of deadline-limited ticks however many rules a huge org has. `POST /api/alerts/rules` locks the org row (`select(Organization.id)...with_for_update()`, the same pattern as the trace-policy cap) and answers 409 `rule_limit` once the org holds `MAX_ORG_RULES` = 200 rules (disabled and `policy_violations` ones counted), per org. A rule to fire is fired under an in-process lock and its row `FOR UPDATE`, then dedup is re-checked, as the violation path does, so overlapping ticks fire and page it once (A17-4). Not closed (acknowledged lows, not re-reported): the resume point is per worker process; a rule whose own check outlasts the deadline is never completed; orgs already over 200 rules keep them.
- **SG-AP3.2 (A17-2, A17-3):** `RESOLVE_THREADS = RESOLVE_QUEUE` (64), so every lookup the queue admits has a thread and none waits behind one held past its deadline; lookups still run on `_resolver`, never the default executor, and are still refused past the queue as `unresolvable_host`. `_Places` bounds an org to `ORG_LOOKUPS` = 2 running lookups and `ORG_CALLS` = 10 calls; a taker past the bound waits in turn for a place handed over through a `concurrent.futures.Future`, so a resolver thread can give it back, and every path (take/give on queue-full, the done-callback, the cancelled-waiter handoff, `post`'s `refs`-guarded `finally`) balances. An org holds at most `ORG_LOOKUPS` of the 64 queue places, so A17-2 now needs 32 orgs, not two. A call past `ORG_CALLS` waits for a place within its deadline instead of being refused as `too_many_calls` (removed), so a rule at the channel bound is paged while another call of its org runs (A17-3). `_dispatch_all` sets `outbound.org` per task, so tick sends run as their rule's org. `/test` is limited to 10 a minute per org (429 `rate_limited`). Not closed (acknowledged lows): the bounds are per process; a call waiting for a place is bounded only by its deadline; an org's own slow names busy its own places (L18-1 here).

## Mutation probe

11 one-line mutants of the SG-AP3 fixes (`backend/scripts/mutants_audit18.py`, AUDIT-16's harness). Each runs against `tests/api/test_{alert_tick,outbound_lookups}.py` and `tests/audit/test_audit_18.py`.

- **Killed (11 of 11):**
  - SG-AP3.1: resume off (`i = 0`), the resume point never advanced (`_resume_at = None`), the turn key reordered so orgs are not interleaved, the cap `>=` as `>`, and `MAX_ORG_RULES` raised.
  - SG-AP3.2: `RESOLVE_THREADS` back to 16, `ORG_LOOKUPS` raised to 64, the `_Places` bound `<` as `<=`, the `_org_lookups` take disabled in `_resolve`, the tick's `outbound.org.set` removed, and the `/test` limit removed.
- On the first run, `MAX_ORG_RULES` raised to 20 000 survived: `test_an_org_has_at_most_max_org_rules` and this audit's cap guard both read the constant, so raising it only moved them along with it, and nothing pinned the approved contract value. `test_rule_cap_is_per_org_and_counts_all_rule_kinds` now asserts `MAX_ORG_RULES == 200` (the value approved under SG-AP3.1's contract addition), and the row is killed. The tick's `org.set` row first pointed at the wrong file (stale) and was corrected to `alert_service.py`.
- No surviving mutants, so there is no low finding for them this round. The per-rule fire lock and the inner dedup re-check (`async with _rule_locks` / the `FOR UPDATE` + re-check) are concurrency guards that a single-process test cannot distinguish from their absence, so they are not in the probe; `tests/api/test_alert_tick.py`'s overlapping-ticks test and `violation_service`'s equivalent cover them, and the row lock is a no-op on SQLite by design.

## Not findings

- `_in_turns` recomputes the turn keys from the current rule set each tick, so a deleted or added rule shifts the rotation but never drops a rule from `order` (the slice returns all of them); `bisect_left(keyed, (_resume_at,))` on a stale key lands at the next key by order, so a deleted resume anchor just resumes at the following rule.
- The dispatch gate (`DISPATCH_CONCURRENCY` = 20) is held while a send waits for an `ORG_LOOKUPS`/`ORG_CALLS` place, so a slow org holds its permits longer than before SG-AP3.2. This does not cross orgs: the gate's waiter queue is FIFO and `_dispatch_all` creates tasks in per-org turn order, so each org's first page is near the front and gets the next freed permit within one `RESOLVE_TIMEOUT_S` cycle, inside the 45 s deadline (verified with 20 slow attacker orgs and a victim).
- `_Places.give` runs under `_lock` on every caller (release, the resolver done-callback, queue-full, the cancelled-waiter except), and `concurrent.futures.Future`'s own methods are thread-safe, so a resolver thread handing a place to an event-loop waiter is race-free; the `turn.cancel()` vs `set_running_or_notify_cancel()` branch returns the place exactly once.
- `post`'s `finally` releases the call's place only `if call and call.refs`, so a call cancelled before `call.start()` acquired a place does not over-release; a successful call's resolver done-callback and the `finally` release the two refs (start + `_resolve`) exactly once each.
- `create_rule`'s `with_for_update()` on the org row is a no-op on SQLite, so two concurrent creates there can both pass the count and exceed 200; on Postgres (production) the lock serialises them. The audit's SQLite runs do not exercise that race.
